# P4 plan: the SABS stress test

Status: **approved by Alireza 2026-11-12, with all nine recommendations in section 6. Built 2026-11-12.**
Last updated: 2026-11-12
Roadmap: `roadmap.md` P4. Builds on P3 (`plans/P3.md`). Screen shape: `design/visual-identity.md`.

**Goal.** Run the full SABS change through the P3 loop, and make the loop strong enough for real regulatory work. You tag only the regulation, and the tool reaches the coverages, rating, forms, claims adjudication and broker channel on its own. It then makes sure nothing affected is silently skipped before sign-off. Still a basic version to use, not a demo. Still no AI.

## 1b. The people board (added 2026-11-12, proposed by Alireza)

> For team structure we should use something simple, like a card board: you add a department, then you add the members, simple as that. Then you can link them together.

A new page, **People**, next to Requests and Company model. Columns are departments or teams. Cards are roles or people.

| On the board | In the model |
|---|---|
| Add a column | A new Department (or Team) |
| Add a card in a column | A new Role (or Person), `member_of` that column |
| Drag a card to another column | The `member_of` link moves (DNA-04: dragging changes meaning, not coordinates) |
| Link two cards | `reports_to`, for example Manager reports to Senior Manager reports to VP |
| Rename or remove a card or column | `node.updated`, or removal of a node that has no other links |

**Why now.** It is the confirm-rename-remove step for the starter template, decided 2026-11-11 (design spec section 3) and not built in P3. It is also the first place the app uses drag and drop (DNA-04).

**One structural choice** (decision 8): board edits change the model directly, without a request, because setting up who is who is not a change to analyse. Every edit is still an event in the log, so nothing is lost and replay still works.

Feature F-37 is added to `traceability.md` on approval, justified by the starter template decision (design spec section 3) and PP-22 (building the model by hand is too slow).

## 2. Mandate mode, without AI

AI extraction of obligations was P1's job, and P1 is paused. So in P4:
1. You pick the regulation (or add it), and it is tagged.
2. You enter each duty it imposes as an Obligation, one at a time, linked to the regulation.
3. The questions then make each obligation owned, sourced and met by a rule ("Which business rule meets...?"). That rule is what links the duty to the operations.

When document upload returns after the checkpoint, step 2 is where AI extraction plugs in. Nothing else changes.

## 3. Impact from a regulation (the main design change)

In P3, impact spreads 2 links out from what you tag. From a regulation that reaches only its obligations. A regulation's effect runs down a chain, so P4 follows that chain all the way down and then spreads 2 links:

- **Walking down the chain is free:** from a Regulation to the Obligations and Rules derived from it, and from a Rule to everything that follows it (`governed_by`). It counts no distance.
- **Everything else counts,** up to 2 links, as in P3.
- **Walking up the chain still counts.** So tagging a single process step does not pull in the regulation's whole footprint. Only tagging the regulation does.

Every affected node still shows its path. For example: *SABS changes → Obligation "Pay medical and rehabilitation first" → Rule "Insurer pays first" → Adjudicate medical and rehabilitation expense → Claims System.*

### What the SABS chain has to reach (criteria 1 and 2)

With the sample company as it is, plus two links, tagging only "SABS changes effective 2026-07-01" reaches:

| Area | Reached through | Status |
|---|---|---|
| Coverages | Rule "Income replacement is optional" → Income replacement benefit; Rule "Insurer pays first" → Medical and rehabilitation benefit | In the seed |
| **Claims adjudication and coordination of benefits** | Rule "Insurer pays first" → Adjudicate medical and rehabilitation expense → Claims System, Accident Benefits Adjuster, and "Does the claimant have workplace benefits?" | In the seed |
| Forms | Income replacement selection → OPCF 47R | **Needs one link:** the selection field follows "Income replacement is optional" |
| Rating | Income replacement selection → read by the Rating Engine → Rate the quote | Same link |
| Broker channel | Select optional benefits → Quote and bind → started by Broker | **Needs one link:** "Select optional benefits" follows "Income replacement is optional" |

**The honest limit.** The sample company is hand-built, and we already know the answer. These tests partly check that our seed is linked correctly. To keep that visible, every link added for this has a `source` attribute citing the document behind it (C-01 to C-05). The real proof comes when you run a change against a model you built yourself.

The seed stays generic. Design spec section 11 lists real systems and partners from `bsa-practice-brief.md`. None of them go into the seed or the repo.

## 4. Architecture and data

All on top of P3. Nothing in the baseline changes before sign-off.

- **Request record:** adds `mode` (request or mandate) and `sponsor` (a Role id).
- **Intake nodes:** Symptom, CauseHypothesis, Evidence, ProposedSolution and SuccessMeasure are added as pending nodes, as in P3. **One taxonomy change is proposed:** a `supports` edge from Evidence to Symptom or CauseHypothesis. A hypothesis then visibly stays a hypothesis until evidence supports it (design spec section 6). Section 6, decision 5.
- **A third kind of pending change:** `update_node`, which becomes a `node.updated` event. Needed because the Integration and DataField questions fill attributes (for example `licence_gating`), not links. The pending update carries the merged attributes, so two answers on one node do not overwrite each other.
- **Gap rules grow a second kind:** attribute rules beside the P3 edge rules. Each one names a node type, the attribute it expects, and the question. The answer is text or "don't know yet". P4 adds the three Integration questions the spec says belong on every Integration node (licence gating, configuration gating, deletion detection) and two DataField ones (authoritative source, null handling).
- **Coverage:** a new table, one row per request and affected node: state (addressed, not applicable, blocked), reason, and when. A node is **addressed automatically** when a pending change touches it. "Not applicable" adds a Decision node with the reason, so it lands in the decision log (criterion 5). "Blocked" adds an Issue.
- **What coverage counts:** processes, systems, data and forms, products, coverages and rules. People and regulation nodes are shown but not counted, otherwise every role two links away would need a verdict. Section 6, decision 4.
- **Prior work:** a pure query. Earlier requests whose tags or impact include any of this request's tagged nodes, plus Requirement, Decision and Issue nodes linked to them.
- **Quality gate:** a list of deterministic checks, each a pure function of the request state. Each check returns pass or fail with a message. Sign-off refuses while any fails, and never blocks on judgment (criterion 6). The checks come from design spec section 6b, the Intake row (rule 16):
  1. A trigger is recorded.
  2. A mode is chosen.
  3. Something is tagged.
  4. Business request: symptom, cause hypothesis and proposed solution are recorded, as separate nodes.
  5. Mandate: at least one obligation, and every obligation is met by a rule.
  6. A sponsor is named.
  7. Coverage is complete: nothing left unaddressed, nothing blocked.
  8. Every "not applicable" has a reason.

## 6. Decisions needed from Alireza

1. **Approve this plan,** or say what to change.
2. **Obligations entered by hand in mandate mode,** with AI extraction waiting for P1. Recommended: yes.
3. **Impact follows a regulation down its chain for free** (section 3). Recommended: yes. Without it, criteria 1 and 2 cannot pass.
4. **Coverage counts processes, systems, data, forms, products and rules,** not people or regulation nodes. Recommended: yes.
5. **Add a `supports` edge** (Evidence to Symptom or CauseHypothesis). This is a taxonomy change. Recommended: yes. It is the only way the model can show what a hypothesis rests on.
6. **Mode as its own question,** pre-selected as mandate for a regulatory change, but changeable. This answers one of the F-35 open questions in design spec section 12. Recommended: yes.
7. **Questions in rounds of 5,** with "ask more". The SABS change has far more than 5 gaps. Recommended: yes.
8. **The people board edits the model directly,** not through a request (section 1b). Recommended: yes. Setting up who is who is setup, not a change to analyse, and every edit is still an event.
9. **Build the people board first in P4.** It is small, it makes the starter template yours before the SABS work runs on it, and it needs nothing from the rest of P4. Recommended: yes.

## 7. Risks

| Risk | Against | Mitigation |
|---|---|---|
| The SABS tests pass because we wired the seed to pass them | Honesty, rule 2 | Every added link cites its source. The limit is stated in section 3 and in the result |
| The free chain pulls in too much | DNA-02, readability | It is free only downward from a regulation or rule. Results are grouped by layer, with counts |
| Coverage review becomes a long chore | DNA-03, the overwhelm the product exists to remove | One node at a time. Nodes touched by a pending change are already addressed. People and regulation nodes are not counted |
| Ten cards on one page | DNA-03 | One active, nine on one line each. Cards that do not apply in this mode are hidden |
| The quality gate starts judging | QGC authority limit | Every check is a pure yes or no over the request state, and each one has a test |

## 8. Out of scope for P4

AI obligation extraction, several options side by side, the gap diff view, generated documents, changing or removing baseline nodes through answers, undoing a sign-off, the model-level coverage view, and visual styling.

## 9. How each acceptance criterion gets tested

| Roadmap P4 criterion | Test |
|---|---|
| 1. Surfaces coverages, rating, forms, claims adjudication and broker channel untold | End-to-end test: tag only the SABS regulation, then assert each area is in the impact set, each with a path |
| 2. Priority of payment shows as a claims and coordination-of-benefits impact | Same test: the claims adjudication step and the workplace benefits decision are affected, through the "insurer pays first" rule, in the Claims lane |
| 3. Integration questions cover licence gating, configuration gating and deletion detection | Test: tag the policy admin to rating integration, and all three questions are asked |
| 4. Coverage cannot reach complete while anything is unaddressed | Test: the gate fails until every counted node has a state, and fails while anything is blocked |
| 5. Not applicable needs a reason, and the reason lands in the decision log | Test: an empty reason is refused; a reason adds a Decision node |
| 6. The quality gate blocks on deterministic failures only | Test per check, plus: sign-off refuses with a failing check and succeeds once all pass |
| 7. Impact on a 300-node model in under two seconds | Test on the synthetic 300-node model from P2 |
| 8. The taxonomy holds without insurance-only changes | Review: the one change, `supports`, applies to any industry |
| 9. Every PH-01 row has a status, every gap a decision | Structure agent run before exit. The four open PH-01 gaps go to Alireza |
| People board (section 1b) | Tests: adding a column and a card creates a Department, a Role and `member_of`; moving a card moves the link; linking adds `reports_to`; replay reproduces the board |
