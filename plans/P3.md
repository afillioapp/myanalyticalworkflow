Last updated: 2026-11-12
Roadmap: `roadmap.md` P3. Screen shape: `design/visual-identity.md`. Practice: `practice/sabs-walkthrough.md`.

**Goal.** A basic, working version of the whole loop that Alireza can use freely, not a scripted demo. Design spec section 3: "a tool genuinely used on real work, from which the demo falls out". Any request, any tags, any answers: the tool shows the impact and why, asks what is missing, turns the answers into pending changes, and sign-off writes them into the model. The next request starts from the updated model. No AI anywhere.

## 1. What you can do with it

1. **Open a new request.** Type what is being asked, in your own words.
2. **Pick its trigger,** one of the seven (F-35).
3. **Tag what it touches,** by searching the model, as in the P2 search. If the thing does not exist yet, add it (type and name), as a pending change.
4. **See the impact:** everything connected to what you tagged, each with the path that explains why.
5. **Answer the questions,** one at a time. They come from what is missing on the affected nodes, so different requests get different questions.
6. **Review the pending changes,** remove any you do not want.
7. **Sign off.** The changes are written into the model, and the graph view shows them.
8. **Open the next request.** It works from the updated model.
9. **Reset** the sample company whenever you want a clean start. Every request and change goes with it.

You can leave a request half done and come back to it.

## 2. Answers are picks, so no AI is needed

A question exists because an edge or attribute is missing, so its answer has a shape:

| Kind of gap | The question | How you answer | Becomes |
|---|---|---|---|
| Missing owner | "Who is responsible for X?" | Pick a role, or add one | `owns` edge |
| Missing performer | "Who does step X?" | Pick a role, or add one | `performed_by` edge |
| Missing system | "In which system is step X done?" | Pick a system, or add one | `executed_in` edge |
| Missing start | "What starts process X?" | Pick a step or event, or add one | `triggers` edge |
| Missing source | "Which regulation or obligation does rule X come from?" | Pick one, or add one | `derived_from` edge |
| Not known yet | Any of the above | "Don't know yet", plus a note | An Issue, linked to the node. A recorded open question, never a guess (rule 2) |

Every gap rule is a row of data: node type, the edge it expects, the question text. Adding a question type later means adding a row.

## 3. A good first request to try

Not a script, just a real starting point. From FSRA's Q&A for insurers (C-02, updated October 14, 2026): FSRA asks insurers to notify it if optional accident benefits are removed or coverage is reduced under a rideshare fleet policy. C-02 does not say how or when, so the honest answer to that question is "don't know yet".

To make that request possible, the sample company gets a few fictional additions (a design choice, not a fact):

## 4. Architecture and data

**Request and SolutionOption are records beside the graph, not nodes in it.** Design spec section 5:
- A **Request** has text, a trigger, tagged node IDs, its answers and a status: open, signed off.
- It opens a **SolutionOption**, an ordered list of change operations (add, modify or remove a node or edge), each linked to the answer that caused it. P3 shows one option, but the data allows several, so later options are not a rewrite.
- **Sign-off promotes** the option. Its operations become normal events (`node.created`, `edge.created` and so on) in one commit. The baseline is still just the event log.
- **Nothing touches the baseline before sign-off.** Pending changes live only in the option.
- **Reset** clears the sample tenant's requests, options and events, then loads the seed again.

**Impact traversal (F-09).** Breadth-first from the tagged nodes, both edge directions, up to a fixed depth (proposed: 2), over the baseline plus the request's pending changes. It keeps the path to each node, so the "why" is never guessed. Order is deterministic: by depth, then layer, then name. A pure function over the graph, like `buildView` in P2.

**Question engine (F-11).** Runs the gap rules over the affected nodes and pending nodes, in a fixed priority, and shows one question at a time, up to 5 per round. It never asks about something the graph already holds, and a question answered or marked "don't know yet" does not come back.

**Storage.** New tables for requests, options, operations and answers, with `tenant_id` and `created_by` like every other table. Migrations as in P0. Runs on the live site's database, so your requests persist between visits.

## 5. Screen shape

From `design/visual-identity.md`:
- A requests list, and one page per request.
- Cards on the request page, in the order of section 1: the request, trigger, what it touches, questions, pending changes, sign off.
- One card active and highlighted, the rest dimmed or collapsed to one line.
- A breadcrumb, for example `Requests › FSRA rideshare notification › Questions`.
- The graph view from P2 stays as it is, and shows the model after each sign-off.

Visual style is not part of P3: plain and readable is enough.

## 7. Risks

| Risk | Against | Mitigation |
|---|---|---|
| The page shows several cards, so several decisions at once | DNA-03 | One active card. Acceptance criterion 8 checks it |
| The impact set is too big to read at depth 2 | DNA-02, the 10-second test | Group by layer, counts first. Lower the depth if it is noisy in use |
| Questions read as generic | The product's main promise | Every question names the node it is about |
| You make a mess while playing | Usability | Reset, and removing pending changes before sign-off |
| A sign-off does not show up in the next request | The loop fails | Acceptance criterion 7, tested in code |

## 8. Out of scope for P3

Several options side by side, the gap diff view, generated documents, document upload and AI, the full interview, editing the model outside a request, undoing a sign-off, verification, export, and visual styling.

## 9. How each acceptance criterion gets tested

| Roadmap P3 criterion | Test |
|---|---|
| 1. Loads with the template, no interview or upload | Seed test: template nodes present after `db:seed` and after reset |
| 2. Request recorded with its trigger, one choice on the screen | Unit test on the request record. Screen check against DNA |
| 3. Same tags, same impact, each with its path | Property test: shuffled input gives identical output. Every affected node has a path |
| 4. The 10-second test | Judged by you, in use |
| 5. 3 to 5 questions, one at a time, never already answered | Unit tests: an answered question does not come back; filling a gap in the model removes its question |
| 6. Answers become pending changes, traced, nothing applied early | Test: the baseline is unchanged until sign-off; every operation links to its request and answer |
| 7. Sign-off writes events, the next request sees them, replay reproduces | End-to-end test: two requests in a row, the second sees the first's changes (the rideshare request is the test fixture) |
| 8. One decision per screen | Checklist against DNA/dna.md |
| 9. PH-01 rows touched have a status | Structure agent run before exit |
